# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Website for **Tábor Oskar**, a Czech summer camp near Rokycany. Next.js (App Router) + TypeScript,
content and copy are in Czech. Public marketing site with a minimal admin path for publishing posts/images.

## Commands

```bash
npm run dev          # start dev server (Turbopack)
npm run dev:no-turbo  # start dev server without Turbopack
npm run build         # production build
npm run start         # run production build
npm run lint          # next lint (ESLint)
npm run migrate <name> # create + apply a Prisma migration (see "Database" below)
docker compose up     # start Postgres + Adminer (+ web if not overridden locally)
npx prisma studio     # DB GUI (alternative to Adminer)
```

There is no automated test suite/runner configured (no `test` script, no Jest/Vitest/Playwright).
`prisma/test.ts` is an ad-hoc manual smoke-test script for the Prisma client, not wired into `npm run`
— execute it directly with a TS runner if needed, don't assume it's part of any pipeline.

Stylelint (`stylelint.config.js`) and Prettier (`.prettierrc`) configs exist but aren't wired to npm
scripts either; run them via their CLIs directly if needed.

## Environment & secrets

Config follows the Docker-secrets convention throughout: most sensitive values are read from a **file**
whose path is given by an `*_FILE` env var (see `src/lib/utilities/load-secret.ts`), not from the env
var's value directly. E.g. `DB_PASSWORD_FILE`, `AUTH_SECRET_FILE`, `GOOGLE_SECRET_FILE`,
`SESSION_PASSWORD_FILE`. In `compose.yml` these point at Docker secrets; locally they point at files
under `secrets/` (gitignored, see `.env.example`). When adding a new secret, follow this same pattern
rather than reading `process.env` directly.

Locally, `.env`/`.env.local` supply everything (see `wiki/environment.md`); under `docker compose`,
env vars come from the compose file and secrets are mounted at `/run/secrets/*`.

## Architecture

### Route-per-feature content convention

Each top-level route under `src/app/<route>/` follows a consistent, co-located file convention —
look for these before assuming content lives elsewhere:

- `page.tsx` — the route component.
- `metadata.json` — `{ title, ... }` consumed both by Next's `metadata` export and by
  `src/app/routes.ts`, which aggregates every route into the nav (`routes.ts` imports each route's
  `metadata.json`/`redirect.ts` — adding a route means updating it too).
- `page.config.json` — larger structured content for that page (e.g. `taborova-hra/[year]/page.config.json`
  is a year → `{ title, description, image }` map driving the dynamic `[year]` route via
  `generateStaticParams`).
- `page.assets.ts` — re-exports of local images so components can import icons/pictures by name.
- `redirect.ts` — a `Redirect` object consumed centrally by `next.config.ts` (see `admin/redirect.ts`,
  `taborova-hra/redirect.ts`). Redirects are declared next to the route they redirect, but registered
  in one place (`next.config.ts`'s `redirects()`), not via file-based redirect mechanisms.

`app.config.json` (in `src/app/`) holds cross-route config not tied to a single page (e.g. external
map links).

### Data layer

- Prisma ORM (`prisma/schema.prisma`) against Postgres, custom client output at `prisma/generated`
  (aliased as `@/prisma/*` in `tsconfig.json`, e.g. `import { Role } from '@/prisma/enums'`).
- Models: Auth.js's `User`/`Account` (extended with a `role: Role` enum — `USER`/`ADMIN`/`MODERATOR`,
  no self-serve elevation, set directly in the DB) plus app models `Post` and `Image`
  (soft-deleted via `deletedAt`, both gated by a `published` flag).
- The Postgres connection URL is assembled at runtime by `src/lib/utilities/postgres-url.ts` from
  discrete `DB_*` env vars + the password secret file — there's no single `DATABASE_URL`.
- **Migrations must go through `npm run migrate <name>`, not `prisma migrate dev` directly.** Prisma
  emits `SERIAL` primary keys, which `migrate.mjs` rewrites to
  `INTEGER GENERATED BY DEFAULT AS IDENTITY` in the generated SQL before deploying — running the raw
  Prisma command skips that rewrite. See `wiki/db.md` for the manual fallback and Adminer/Studio info.
- In production, migrations are applied at container startup (`Dockerfile` CMD: `prisma migrate deploy`
  before `node server.js`), not during the build.

### Auth

Two independent session mechanisms coexist:

- **Auth.js (NextAuth v5)** (`src/lib/auth.ts`) — Google OAuth via `PrismaAdapter`, JWT session
  strategy, `role` copied onto the JWT/session in the `jwt`/`session` callbacks. This is what gates
  admin actions: `src/app/api/post/new/route.ts` checks `session.user.role === Role.ADMIN` before
  calling `createPost`. Visiting `/admin` redirects straight into the Google OAuth flow
  (`src/app/admin/redirect.ts` → `/api/v1/auth/connect/google`).
- **iron-session** (`src/lib/session/session.ts` + `session-data.ts`) — a separate, currently-unused-
  outside-its-own-module lightweight session helper (`SessionData { user?: { id, email } }`,
  cookie `sid`), independent of Auth.js. Check both when working on anything session-related; don't
  assume `auth()` is the only mechanism.

Server-side mutations go through `src/lib/actions/` (e.g. `post.ts`'s `createPost`), which validate
input with `zod` schemas from `src/lib/validators/` before touching Prisma — follow this
validate-then-persist shape for new mutations rather than trusting request bodies.

### Components

`src/components/` is organized by role, not by feature — `auth/`, `common/`, `data/`, `geo/`,
`layout/`, `navigation/`, `progressive/`, `reactive/`. Each component gets its own folder:
`<name>.component.tsx`, `<name>.module.css` (CSS Modules, alongside MUI/Emotion for MUI components —
both styling approaches are in active use, match whichever the component you're touching already
uses), `<name>.types.ts`, and an `index.ts` barrel export. Follow this shape for new components.

### Harvester (content import, separate stack)

`harvester/` is an independent Python project (BeautifulSoup + `markdownify` + `requests`) that scrapes
the camp's old Drupal site (tabor-oskar.cz) and either writes JSON config directly
(`themed-game.py` → `src/app/taborova-hra/[year]/page.config.json`) or POSTs scraped posts/images to
the running web app's `/api/post/new` endpoint (`posts.py` via `harvester/lib/api.py`), authenticated
with an admin session cookie pasted in manually — i.e. it's a real client of the admin-only API, not a
DB-direct import. It has its own `requirements.txt`/venv and is excluded from the CI build trigger path
filter. See `harvester/CLAUDE.md` for details when working in that directory, and `wiki/harvester.md`
for the script reference.

### Path aliases

`@/*` → `src/*`, `@/prisma/*` → `prisma/generated/*` (defined in `tsconfig.json`).

### Deployment

Multi-stage `Dockerfile` (Next `output: 'standalone'`); `docker compose up` runs `db` (Postgres),
`adminer` (DB GUI on :8080), and `web`. CI (`.github/workflows/deploy.yml`) builds and pushes the image
to a private registry on push to `master`, ignoring changes confined to `wiki/`, `harvester/`, or
`README.md`.
